# datagokr-mcp

**공공데이터를 "찾아 주는" 시스템이 아니라, 목표에 맞게 "고르고 잇는 방법"을 근거와 함께 알려 주는 시스템.**

> "성수동 상권 변화를 월 단위로 추적하고 싶다" →
> 어떤 데이터를(소상공인 상가정보 15012005 + 일반음식점 인허가 15154916) · 왜(실측으로 확인한 갱신·범위·키) ·
> 어떻게 잇나(필지고유번호 PNU로, 연속지적도를 거쳐) · 무엇을 조심하나(검증 호출 조건, 필수 파라미터) · 바로 돌릴 코드

공공데이터포털(data.go.kr)에는 9만 6천 개가 넘는 데이터가 있다. 목록은 충분하다. 부족한 것은 **판단**이다.
어떤 데이터가 실제로 호출되는가, 지금도 갱신되는가, 무엇과 무엇이 이어지는가, 이 코드값은 무슨 뜻인가.
이 판단을 사람이 매번 다시 하지 않도록, 그리고 AI가 그럴듯하게 지어내지 않도록, **검증된 지식으로 쌓아 두고 꺼내 쓰는 것**이 이 프로젝트다.

## 1. 왜 만들었나 — 문제의식

**목록은 있는데 지도가 없다.** 포털의 데이터는 부처가 등록한 순서와 분류(BRM 정책분야)로 놓여 있다.
그런데 사람이 가진 질문은 부처를 가리지 않는다. "우리 아이를 어디에 맡길까"는 어린이집(보건복지부)과 유치원(교육부)과
초등돌봄(교육청)과 다함께돌봄(보건복지부)을 함께 봐야 답이 된다. 같은 병원이 건강보험심사평가원에서는 `ykiho`,
국립중앙의료원에서는 `hpid`, 지자체 인허가에서는 또 다른 번호로 등록되어 있다. 목록만으로는 이 연결이 보이지 않는다.

**메타데이터는 실물과 다르다.** 포털에 "API"라고 적혀 있어도 호출해 보면 응답이 없거나, 필수 파라미터의 예시값이
만료되었거나, 다른 데이터의 코드가 있어야만 부를 수 있는 경우가 흔하다. 적힌 갱신 주기와 실제 갱신이 다르고,
표준데이터는 파일 없이 API로만 나오기도 한다. 메타만 보고 추천하면 쓸 수 없는 데이터를 추천하게 된다.

**AI는 공공데이터를 아는 척한다.** 언어모델은 데이터 이름과 대략의 용도는 알지만, 오늘 올라온 입찰공고나 지목 코드
`08`이 "대(垈)"라는 것, 두 데이터가 실제로 어떤 열로 이어지는지는 모른다. 모르는 것을 그럴듯하게 채운다.
조인 조건을 지어내고, 코드값의 뜻을 추측하고, 존재하지 않는 파라미터를 넣는다.

그래서 이 시스템은 **검색 엔진이 아니라 전략 엔진**으로 설계했다. 목표를 받으면 ① 어떤 데이터를 ② 왜(법적 근거·갱신·실측 결과)
③ 어떻게 이어서(조인 키·순서·함정) ④ 바로 실행할 코드까지 — 사람이 읽어도, 에이전트가 받아도 바로 쓸 수 있는 구조로 돌려준다.
그리고 그 모든 문장에 근거를 단다.

## 2. 설계 사상 — 열두 가지 원칙

### ① 실물 우선 — 메타가 아니라 직접 불러 본 것만 믿는다

모든 대상 데이터는 실제로 활용신청하고, 키를 받고, 호출하고, 내려받고, 컬럼마다 통계(타입·빈 값 비율·유니크 수·상위 값)를 냈다.
포털 설명은 출발점일 뿐이고, 지식이 되는 것은 실측이다.

이 원칙 덕분에 메타만 봐서는 알 수 없는 것들이 드러났다.
- 가맹 브랜드 API의 "최신 날짜 2018년"은 데이터가 낡은 게 아니라, 검증 호출이 명세 예시값(`기준연도=2017`)을 그대로 썼기 때문이었다. 이런 "예시값 착시"가 26건이었다.
- 표준데이터의 학교ID(`B000…`)와 나이스 학교코드는 **값이 하나도 겹치지 않았다**(0/12,011). 이름과 주소로 매핑표를 따로 만들어야 했다.
- 공동주택 기본정보 API는 응답이 목록이 아니라 단건 객체로 와서, 성공한 호출을 실패로 판정하고 있었다.
- 실패 판정이던 데이터 2건은, 필요한 코드(ykiho, kaptCode)를 다른 데이터의 전수 목록에서 받아 넘기자 살아났다.

### ② 근거 없는 사실은 사실이 아니다 — 모든 "왜"는 근거를 단다

데이터에 대한 모든 진술은 **claim**(사실 진술)으로 저장한다. claim은 값과 함께 근거를 하나 이상 가진다.
근거의 종류는 여섯 가지다: `measured`(실측) · `law`(법령 원문) · `admin_review`(사람의 검토 결정) · `portal_meta`(포털 등록값) ·
`inferred`(AI 초안) · `user`(사용자 피드백).

이 가운데 **실측·법령·검토 결정 중 하나가 있어야만 "사실"로 인정**한다. 포털 메타나 AI 추론만 있는 진술은 설명서에
"(미확인)"으로 표시되고 전략 응답의 근거로 나가지 못한다. 전략 응답의 모든 추천 이유는 claim id를 인용하고,
서버는 인용된 claim이 실제로 있고 근거가 있는지 검사한 뒤에야 응답을 내보낸다.

### ③ 선언된 조인만 쓴다 — AI는 조인을 만들지 않는다

데이터를 잇는 방법은 **Edge**로 미리 선언한다. "A의 이 열과 B의 저 열이 이어진다, 관계는 다대일이다, 코드 체계가 달라 이 매핑표를 거친다,
변환 규칙은 이것이다"를 파일로 적어 두고, 실제 데이터로 매칭률을 잰다(2,089개 선언, 1,315개 실측, 중앙값 100%).

AI는 이 선언된 Edge 중에서 **고르기만** 한다. 경로가 없으면 없다고 말하고, 그것을 "공백"으로 보고한다.
AI에게 조인 조건을 생성하게 하면 그럴듯하지만 틀린 조인이 섞인다. 선택하게 하면 틀릴 수가 없다.

변환이 필요한 연결은 **규칙 코드**로 둔다. 실거래 신고의 시군구+읍면동+번지를 필지고유번호(PNU)로 조립하는 규칙(R-07),
좌표를 그 점이 속한 필지로 바꾸는 규칙(R-12), 행정구역 이름을 코드로 바꾸는 규칙(R-14) 같은 것들이다.
모두 테스트가 있는 함수이고, 코드 생성기가 그대로 가져다 쓴다.

### ④ 모델이 이미 아는 것은 가치가 낮다 — 시의성(novelty)

법령 본문이나 행정 규칙처럼 이미 널리 공개되어 언어모델이 학습한 내용은, 이 시스템이 따로 담아 줄 가치가 낮다.
반대로 **오늘 올라온 의안, 어제 낙찰된 입찰, 이번 주 급식 식단, 지금의 대기질**은 모델이 절대 모른다.
그래서 데이터를 고를 때 "AI가 이미 아는가"의 반대를 점수(시의성)로 두었다. 법령도 본문 자체보다
"어떤 데이터가 어느 법 몇 조 때문에 존재하는가"라는 연결로 담는다.

### ⑤ 집계보다 원천, 일부보다 전수, 고립보다 연결

통계·지역 집계보다 **건별 원천**(공고 한 건, 계약 한 건, 점포 하나, 필지 하나)을 위에 둔다. 집계는 원천에서 언제든 만들 수 있지만
그 반대는 안 된다. 전체를 끝까지 받을 수 있는(**전수**) 데이터를 더 높게, 다른 데이터와 이어지는 **조인 키**(사업자번호·PNU·법정동코드·
기관코드 …)가 있는 데이터를 더 높게 본다.

매핑과 코드표를 만들 때도 같은 원칙을 썼다. 표본 1,000건으로는 매칭률이 의미가 없어서, 원장마다 **전수 목록**을 끝까지 받았다
(병원 8만, 공동주택 2만 2천, 버스정류장 10만, 기관코드 41만 8천, 실거래 6개월 24만 건).

### ⑥ 부처의 분류가 아니라 국민의 질문으로 묶는다

포털의 정책분야 분류는 출발점일 뿐이다. 같은 시스템의 데이터가 여러 분야에 흩어져 있으면(조달청 나라장터 API 18종이 네 분야에,
공정거래위원회 데이터 266건이 다섯 분야에) **원래 시스템 기준으로 다시 모았다**. 잘못 분류된 것은 지우지 않고 제자리로 옮겼다.

부처가 달라 분류는 다르지만 국민에게는 같은 질문인 것들은 **맥락(context)**으로 잇는다 — 영유아 돌봄, 노후 돌봄, 동네 상권,
"이 땅에 무엇을 지을 수 있나", "이 회사 지금 괜찮나" 등 42개. 맥락에는 차원이 있다: 같은 생애 질문 · 같은 필지에 겹치는 규제 · 같은 행정구역 지표 ·
같은 조인 키 · 같은 원천 시스템 · 같은 개념의 다른 기준 · 돈과 거래의 흐름.

국토 분야는 다시 **법 체계**로 층을 세웠다. 국토기본법 아래 계획(국토계획법) → 규제(용도지역) → 개발사업(도시개발·정비·산업단지) →
정보 원장(필지·건물)으로 이어지는 구조다. 데이터 하나가 법 체계의 어느 층에서 나왔는지를 알면, 그 데이터가 무엇을 말할 수 있고
무엇을 말할 수 없는지가 보인다.

### ⑦ 코드표가 품질을 가른다 — 필드부터 보고 코드를 모은다

`lndcgrCode=08`, `prposArea1=14`, `clCd=11` — 코드표 없이는 뜻을 알 수 없다. 코드표가 있으면 AI가 조회 조건을 정확히 넣고
(종합병원만 → `clCd=11`) 결과를 사람의 말로 풀 수 있다. 없으면 코드값을 그대로 넘기거나 뜻을 지어낸다.

순서가 중요했다. 생각나는 코드표부터 모으지 않고, **대상 데이터의 필드 1,910개를 전부 판정**해서 "코드표 없이는 뜻을 알 수 없는 필드"
(192개)부터 정했다. 그다음 여러 데이터가 함께 쓰는 국가 표준(법정동·기관코드·국가·통화·항구·HS·NCS·지목)부터 원천을 찾아 **전수로** 확보했다.
지목 28종은 공간정보관리법 제67조의 열거 순서가 곧 코드 번호이므로 법령 원문을 근거로 삼았고, 실제 데이터 표본으로 번호를 대조했다.
코드표마다 "공식 전체 / 전수 원장에서 쓰이는 값 전부 / 표본에서 본 값만"을 구분해 적는다.

### ⑧ 세 층은 섞이지 않는다 — 검증 · 후보 · 단서

| 층 | 뜻 | 전략 응답에서 |
|---|---|---|
| **verified** (1,583) | 실제 호출·다운로드·통계까지 검증 | 정식 추천 · 조인과 파이프라인에 참여 |
| **candidate** (66) | 선정했지만 검증 실패·보류 | "선정됐으나 미검증"으로만 · 조인 불가 |
| **catalog** (96,110) | 포털 전체 목록, 메타만 | "직접 확인이 필요한 단서" 최대 10개 |

층을 나눈 이유는 정직함 때문이다. 검증하지 않은 것을 검증한 것처럼 말하지 않으면서도, 아직 손대지 못한 9만 건을 버리지 않는다.
단서가 쓰이고, 쓰인 단서가 검증을 통과하면 위 층으로 올라간다 — **노출 → 사용 → 승격**이 나머지를 채워 가는 길이다.
승격 조건(근거 있는 claim 3개 이상, Edge 1개 이상)은 스키마가 강제하므로 사람도 우회할 수 없다.

### ⑨ 접근이 불편한 것은 깎지 않고 설명한다

포털에는 목록만 있고 실제 API는 기관 사이트에 있는 데이터가 많다(브이월드 연속지적도, 나이스 급식, 서울 실시간 도시데이터,
법제처 법령 …). 이런 데이터를 점수에서 깎지 않았다. 가서 키를 받으면 쓸 수 있고, 오히려 핵심 원장인 경우가 많다.
불편함은 점수가 아니라 **접근 경로**로 드러낸다 — 어느 사이트에서, 어떤 절차로, 어떤 이름의 파라미터로 키를 넣는지
(`knowledge/key_issuers.yaml`, 22곳).

### ⑩ 사람이 확정하고, 결정은 기록으로 남는다

부문을 어떻게 나눌지, 무엇을 대상으로 삼을지, 어떤 조인을 확정할지, 골든셋의 정답 전략이 무엇인지는 **사람이 정한다.**
자동화는 후보를 내고 사람이 고른다.

그리고 그 결정은 대화로 흘러가지 않고 파일로 남는다. 부문 검토에서 내린 결정(무엇을 남기고 왜 뺐는지)은
`knowledge/sectors/_review_log.md`에 날짜·결정자와 함께 기록되고, 생성기가 그 줄을 `admin_review` 근거로 인용한다.
"왜 이 데이터인가"라는 질문에, 몇 주 전 누가 어떤 이유로 그렇게 정했는지까지 거슬러 올라갈 수 있다.

### ⑪ 파일이 원본이고, 나머지는 모두 파생물이다

지식의 원본은 `knowledge/` 아래 **YAML 파일**이다. git으로 변경 이력을 남기고, diff로 리뷰하고, 승인한다.
DB·검색 색인·설명서·임베딩은 모두 이 파일에서 다시 만들 수 있는 **파생물**이라 손으로 고치지 않는다.

모든 파일은 스키마(pydantic → JSON Schema)로 검증된다. 오타 하나, 존재하지 않는 키 참조 하나, 선언되지 않은 Edge를 쓰는 레시피 하나도
`python -m pds validate`가 막는다. 새로운 개념이 필요하면 스키마와 마이그레이션을 같이 올리며 앞으로 간다.

### ⑫ 키는 사용자 것이고, 모르는 것은 모른다고 말한다

이 저장소에는 **어떤 키도 없다.** 포털 데이터는 각자 활용신청하고, 외부 사이트는 각자 발급받는다. 시스템은 키 발급 절차를 안내할 뿐
사용자의 키를 보관하거나 대신 호출하지 않는다.

그리고 모르는 것은 모른다고 한다. 포털에 데이터가 없는 업무 영역(정치자금, 규제 원문, 감사 결과 …)은 **공백(gap)**으로 기록하고
전략 응답에 그대로 보고한다. 조인 경로가 없으면 "조인 경로 미선언", 표본으로 판정할 수 없는 조인은 "실측 보류",
갱신 주기를 아직 관찰하지 못했으면 "근거 없음"이라고 적는다. 빈칸을 그럴듯한 말로 채우지 않는 것이 이 시스템이 AI와 다른 점이다.

## 3. 지식은 어떤 모양인가

```
                           ┌───────────── 법 체계 (domain) ─────────────┐
                           │ 국토기본법 → 계획·규제 / 개발사업 / 국토정보 │
                           └──────────────────┬─────────────────────────┘
 정책분야 16 → 부문 81 → 세부 부문 312 ──────────┤ 맥락(context) 42: 부처를 가로지르는 국민의 질문
                                                │
   Dataset (verified 1,583 · candidate 66)      │      Law 43 (법제처 현행 원문)
     ├─ claims: 근거 있는 사실 10,983 ──────────┼───── evidence: 실측 · 법령 · 검토 결정
     ├─ services: 호출 방법 (키·파라미터·페이징)  │
     ├─ schema.fields: 실측 컬럼 ── code_list ───┼──→ CodeList 120 (법정동·기관·지목·국가·통화·HS …)
     │                          └─ semantic_type ┼──→ Key 66 (사업자번호·PNU·법정동·ykiho …)
     └─ Edge 2,089 ── via_mapping ───────────────┼──→ Mapping 7 (학교 99% · 병원 98% · 공동주택 · 정류장 …)
          └─ transform ──────────────────────────┴──→ Rule (R-07 PNU 조립 · R-12 좌표→필지 · R-14 이름→코드)
   Recipe: 맥락의 데이터들을 선언된 Edge로 잇는 파이프라인 (골든셋 정답의 출발점)
   Gap: 포털에 없는 업무 영역
```

| 엔티티 | 뜻 | 위치 |
|---|---|---|
| Dataset | 데이터 한 건 — 호출 방법·실측 컬럼·근거 있는 사실·검증 결과 | `knowledge/datasets/` |
| Claim | 값 + 근거(실측·법령·검토) + 유효기간 — 모든 "왜"의 단위 | 데이터셋 yaml 안 |
| Key | 데이터를 가로지르는 식별자와 그 원장 | `knowledge/keys/` |
| Mapping | 같은 대상을 다른 코드로 가진 두 체계의 대응표 | `knowledge/mappings/` |
| Edge | 선언된 조인·호출 체인 + 실측 매칭률 | `knowledge/edges.yaml` |
| CodeList | 코드값 → 뜻 (전체·스캔·관측 구분) | `knowledge/codes/` |
| Context | 부처를 가로지르는 같은 질문의 묶음 | `knowledge/contexts/` |
| Recipe | 검증된 파이프라인 (골든셋) | `knowledge/recipes/` |

## 5. 써 보기

```bash
python -m venv .venv && .venv/Scripts/activate        # macOS·Linux: source .venv/bin/activate  (Python 3.11+)
pip install -e .
cp .env.example .env                                   # CLAUDE_API_KEY만 있어도 채팅이 된다. Postgres는 선택
python -m pds setup                                    # 한 번에 세팅 (아래 표)
python -m pds serve --port 8765                        # 웹 채팅 + API → http://127.0.0.1:8765
```

`setup`이 하는 일 — 원본은 파일(`knowledge/` + 포털 목록 스냅샷)이고 DB는 그로부터 만드는 파생 인덱스다:

| 단계 | 내용 | 없으면 |
|---|---|---|
| 지식 검증 | `knowledge/`(git에 있음) 스키마·참조 검사 | — |
| 포털 목록 스냅샷 | GitHub Release `data-20260731`의 `pds-data-20260731.zip`(46MB)을 받아 `data/processed/`에 푼다. 못 받으면 포털에서 새로 만든다(`download`+`build`, 수십 분) — `--rebuild`로 강제 | 단서(catalog) 검색만 빠진다 |
| 설명서 | `docs/dossiers/` 생성 | 데이터 상세의 설명서가 빈다 |
| Postgres | `.env`의 `POSTGRES_*`가 있으면 마이그레이션(`sql/`) → 목록·분류·점수 적재 → 지식 엔티티 적재. `--kg`면 지식 그래프도 | 서비스는 DB 없이 돈다 |
| 색인 | 검색 색인(`data/processed/service_index.pkl`) | 첫 요청 때 만든다 |

백업·복원 — DB 스키마를 다른 시스템과 같이 쓰는 경우가 있어 **`pds_*` 테이블만** 다룬다:

```bash
python -m pds db-backup                    # backups/pds-YYYYMMDD/*.parquet + manifest.json
python -m pds db-restore backups/pds-YYYYMMDD --yes
python -m pds data-pack                    # 스냅샷 zip (Release에 올리는 파일)
```

| 경로 | 내용 |
|---|---|
| `/` | 웹 채팅 — 대화 + 진행 요약·출처 + 전략 패널(데이터·조인·순서·실행 코드·단서) + 데이터 설명서 서랍 |
| `POST /api/chat` | 대화 (도구: 전략 수립·검색·상세·코드표) |
| `POST /api/plan` | `{goal}` → 전략 응답 ([KNOWLEDGE-SPEC §4](KNOWLEDGE-SPEC.md)) — 근거·조인 규칙을 서버가 검사 |
| `GET /api/search?q=&tier=` | 세 층 검색 |
| `GET /api/datasets/{id}` · `/api/codes/{id}?q=` | 상세·설명서 · 코드 조회 |

**웹 화면**은 빌드된 결과(`web/dist`)가 저장소에 들어 있어 받자마자 뜬다. 원본은 `frontend/`(React 19 + Vite,
BigValue 디자인 시스템 `@bv-ds/ui` Agent 컴포넌트) — 디자인 시스템 레지스트리가 사내 전용이라 외부에서는 다시 빌드할 수 없다.
다시 빌드하려면(사내):
`cd frontend && npm install && npm run build` → `web/dist`를 서버가 `/`에서 서빙한다. `@bv-ds/*`는 사내 레지스트리
패키지라 `frontend/.npmrc`(git 밖)에 레지스트리 설정이 필요하다. API(`/api/*`)는 빌드 없이도 동작한다.
개발 중에는 `npm run dev`(5173, `/api`는 9001로 프록시).

**MCP** (Claude Desktop 등): `python -m pds mcp` — 도구 `plan_public_data_strategy` · `search_datasets` · `get_dataset` ·
`list_code_lists` · `lookup_code`, 리소스 `dataset://{id}`.

```json
{ "mcpServers": { "datagokr": { "command": ".../.venv/Scripts/python.exe", "args": ["-m", "pds", "mcp"], "cwd": ".../datagokr-mcp" } } }
```

**지식을 더 쌓는 명령**: `gen-dataset`(데이터셋·claim) · `pds.probe.fullpull`(전수 원장) · `pds.mapping.build_*`(매핑) ·
`pds.codes.needs`/`build`(코드표) · `pds.edges.auto` + `pds.probe.join`(Edge 실측) · `pds.laws.fetch`(법령) ·
`pds.probe.observe`(갱신 관찰, 매주) · `validate`(검증) — 자세한 흐름은 [`KNOWLEDGE-SPEC.md` §7](KNOWLEDGE-SPEC.md).

키: `.env.example` 참고. 저장소에는 키·계정·세션이 없다(`.env`, `secrets/`는 git 밖).
포함된 파생 데이터(코드표·매핑·실측 통계)는 공공데이터포털 개방 데이터에서 만든 것으로, 원 데이터의 이용허락 조건을 따른다.

## 6. 한계와 다음 단계

- **갱신 주기**는 아직 기준선(2026-09-30)만 있다. 매주 관찰을 쌓아야 "실측 주기"라는 근거가 생긴다.
- **설명문과 레시피는 AI 초안**이다(승인 전 표시). 골든셋의 정답 전략은 사람이 확정해야 한다.
- **검색**은 글자 단위 BM25와 의미 임베딩(multilingual-e5, 선택 설치 `pip install -e .[semantic]`)을 합친 관련도다. 고정 개수가 아니라 1위 대비 기준값으로 자르고, 채팅에서는 LLM(Haiku)이 관련도를 다시 매겨 글자만 겹친 데이터를 거른다. 조인이 없는 관련 데이터도 "참고"로 남긴다. 평가: `python -m pds eval-plan` (정답표 `evals/plan_recall.yaml`).
- **매핑의 한계**: 복지시설(주소 없는 두 목록)과 정류장(좌표 없는 표준 목록, 길 양쪽 같은 이름)은 매칭률이 낮다 — 낮은 대로 기록했다.
- **코드표**: 기관 고유 코드 150여 개는 명세서 첨부 문서에만 있다. 표준산업분류(KSIC)·세관부호는 포털에 원천이 없다.
- **남은 대상**: 실패 375건 재시도, 미검토 포털 API 1,563건, 키 없는 외부 사이트 대기 359건.
